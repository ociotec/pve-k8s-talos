# Prometheus CPU and memory sizing

Research checked on 2026-10-19. Prometheus defaults and implementation details below are pinned to **v3.13.2**; the Go GC guide is a living document. This note contains no cluster-specific recommendation.

## What the official sources establish

The reviewed Prometheus documentation does **not** prescribe a universal CPU/RAM formula based on Kubernetes workers, nor a fixed RAM cost per time series. Its explicit capacity formula is for **disk**: retention duration × ingested samples/second × average bytes/sample. The documented 1–2 bytes/sample describes compressed storage, not RAM. Do not use that figure to size memory. [Storage](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/storage.md#operational-aspects)

The relevant workload dimensions are:

| Dimension | Evidence and practical implication |
| --- | --- |
| Head series and series churn | The TSDB Head maintains series and exposes `prometheus_tsdb_head_series`, `prometheus_tsdb_head_series_created_total`, and `prometheus_tsdb_head_series_removed_total`. Measure resident series and creation/removal rates rather than counting nodes alone. This measurement advice is an operational inference from the implementation, not a vendor sizing formula. [Head implementation](https://github.com/prometheus/prometheus/blob/v3.13.2/tsdb/head.go) |
| Sample ingestion and scrape interval | `scrape_interval` controls collection frequency. For a stable set of scraped series, a longer interval produces fewer samples per second; it does not remove their distinct label sets. Assess interval and cardinality separately. [Configuration](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/configuration.md#scrape_config) |
| Query selection and concurrency | Large input selections can overload the server, even if aggregation returns a single value. Input series, time range, evaluation steps and simultaneous queries belong in a representative workload test. `query.max-concurrency` defaults to 20 and `query.max-samples` to 50,000,000 **per query**; these are admission controls, not a total memory budget. [Query guidance](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/querying/basics.md#avoiding-slow-queries-and-overloads), [Flags](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/command-line/prometheus.md) |
| Recording and alerting rules | Rules evaluate periodically; recording rules persist their results as additional series. They can replace repeated expensive interactive expressions with precomputed results, while adding evaluation work and ingestion. [Recording rules](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/recording_rules.md) |
| Restart and recovery | Recent incoming data is protected by a WAL that is replayed on restart. The optional, experimental memory snapshot on shutdown reduces replay work after a suitable shutdown. Include recovery in validation instead of considering only steady state. [Storage](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/storage.md#on-disk-layout), [Snapshot feature](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/feature_flags.md#memory-snapshot-on-shutdown) |
| Heap, mapped files and page cache | Prometheus writes Head chunks for memory mapping. Go's soft limit covers runtime-managed memory, not every source of process/container memory; Prometheus also explicitly discusses page-cache growth. Compare Go memory, process memory and container accounting instead of treating them as interchangeable. [Chunk flag](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/command-line/prometheus.md), [Go memory limit](https://go.dev/doc/gc-guide#Memory_limit), [Experimental uncached I/O](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/feature_flags.md#use-uncached-io) |

Historical block retention and the active Head are different storage layers. Reducing retention can save disk, but is not a documented proportional reduction of the live heap. [Storage layout](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/storage.md#on-disk-layout)

## Runtime settings are controls, not resource sizing

In v3.13.2, `--auto-gomaxprocs=true` adapts Go execution parallelism to a Linux container CPU quota, `--auto-gomemlimit=true` selects a Go memory limit from container/system memory, and `--auto-gomemlimit.ratio=0.9` is the default ratio. They do not select or provision Kubernetes requests/limits. An explicit `GOMAXPROCS` or `GOMEMLIMIT` environment variable takes precedence over the corresponding automatic helper. The exact upstream dependency versions are recorded in Prometheus's `go.mod`. [Flags](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/command-line/prometheus.md), [Initialization](https://github.com/prometheus/prometheus/blob/v3.13.2/cmd/prometheus/main.go), [Dependencies](https://github.com/prometheus/prometheus/blob/v3.13.2/go.mod), [automaxprocs precedence](https://github.com/uber-go/automaxprocs/blob/v1.6.0/maxprocs/maxprocs.go), [automemlimit precedence](https://github.com/KimMachineGun/automemlimit/blob/v0.7.5/memlimit/memlimit.go)

`GOMEMLIMIT` is **soft**, not an RSS/cgroup ceiling or an OOM guarantee. Go describes it as runtime memory `Sys - HeapReleased`. A limit close to or below required live memory can cause excessive GC. To avoid indefinite GC thrashing, Go limits GC CPU consumption to roughly 50% over a CPU-time window and may exceed the soft memory limit. This mechanism does not by itself prove that CPU throttling caused a particular OOM. [Go memory-limit explanation](https://go.dev/doc/gc-guide#Memory_limit)

Go recommends leaving **5–10%** for memory outside the runtime in the specific case of a controlled container environment. This is a Go rule of thumb, not a Prometheus guarantee that 90% is always safe. Prometheus's automatic 0.9 ratio likewise does not establish a universal sizing margin. Additional workload/recovery headroom must be justified by measurements. [Go suggested uses](https://go.dev/doc/gc-guide#Suggested_uses), [Prometheus defaults](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/command-line/prometheus.md)

`GOGC` trades GC CPU against heap growth: decreasing it generally increases collection work while reducing heap overhead; increasing it generally does the reverse. It cannot shrink the live dataset. Prometheus's documented `runtime.gogc` default is 75; its implementation initializes the default from an explicit `GOGC` environment variable when present, and an explicit YAML `runtime.gogc` can set the effective value. Inspect the effective configuration before tuning it. [Go GOGC](https://go.dev/doc/gc-guide#GOGC), [Runtime configuration](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/configuration.md#configuration-file), [Default selection](https://github.com/prometheus/prometheus/blob/v3.13.2/config/config.go), [Applying runtime configuration](https://github.com/prometheus/prometheus/blob/v3.13.2/cmd/prometheus/main.go)

## Available strategies and tradeoffs

1. **Reduce ingestion/cardinality:** remove unnecessary metrics or unstable label dimensions at their source; use target relabeling and `metric_relabel_configs` to retain required data. Adjust scrape intervals according to required resolution. Limits such as `sample_limit`, label limits, `body_size_limit` and `target_limit` protect ingestion, but exceeding them can fail an entire scrape or reject targets; they do not silently downsample safely. [Scrape configuration and relabeling](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/configuration.md#scrape_config)
2. **Bound query work:** narrow selectors, avoid excessive ranges/steps, use recording rules for repeatedly expensive calculations, and tune query concurrency/sample/time limits. Lowering limits can produce rejected or timed-out queries; precomputation adds persistent series and scheduled work. [Query advice](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/querying/basics.md#avoiding-slow-queries-and-overloads), [Recording rules](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/recording_rules.md), [Flags](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/command-line/prometheus.md)
3. **Scale resources after measuring:** choose CPU and memory using representative ingestion, queries, rules, compaction and restart tests. This is this note's proposed operating method, not an official numeric formula. Increasing resources does not eliminate unbounded cardinality or query inputs; the official query guidance explicitly warns about overload from large selections. [Query guidance](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/querying/basics.md#avoiding-slow-queries-and-overloads)
4. **Partition collection and federate aggregates:** separate target sets among servers; `hashmod` relabeling can implement deterministic target partitioning. Official federation supports local detailed views and a global server that retains selected aggregated series. Partitioning is an architectural choice; federation is not automatically a distributed engine for arbitrary full-resolution queries. [Relabel actions](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/configuration.md#relabel_config), [Federation](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/federation.md)
5. **Remote storage / Agent mode:** remote write forwards ingested samples but a normal server still maintains its local TSDB. Remote-write queues have configurable per-shard capacity and concurrency, so remote write adds buffering/work rather than guaranteeing a smaller collector. Agent mode uses its WAL-oriented storage and does not initialize the local query/rule engines; use it when queries and rule processing can live elsewhere. Remote read still evaluates PromQL in the querying Prometheus server. [Storage integrations](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/storage.md#remote-storage-integrations), [Remote-write queues](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/configuration/configuration.md#remote_write), [Agent/server initialization](https://github.com/prometheus/prometheus/blob/v3.13.2/cmd/prometheus/main.go), [Agent flags](https://github.com/prometheus/prometheus/blob/v3.13.2/docs/command-line/prometheus.md)

## Suggested measurement procedure — local engineering guidance

Record Head series/churn, ingested sample rate, process/container memory and CPU, GC behavior, scrape durations, query latency/concurrency and rule duration. Observe representative busy periods and test WAL recovery with the intended resource envelope. Relate resource changes to those workload changes; document any empirical bytes/series estimate as a measurement for that workload/version, not a universal constant. Validate CPU and RAM together: memory tuning changes GC work, and query load changes both allocation and CPU demand. The rationale comes from the source-backed dimensions above; the procedure and any selected percentile or extra margin are local engineering choices.

No configuration or deployment changes are required for this research note.
